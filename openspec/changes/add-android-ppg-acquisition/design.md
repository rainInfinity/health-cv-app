# Design

## Context

动机见 `proposal.md`。当前 `apps/native/App.tsx` 仍显示 Hello World，`packages` 中已有云端客户端但没有采集包；应用认证服务只有云端配置存在时才组装，不能将该条件变成离线采集的前提。

现有 Android 基线为 Expo 57、React Native 0.86.3、Nitro 0.37.1，开发说明记录了 Pixel_5／API 37／arm64 模拟器构建，不代表自研 Nitro 对象、视图或采集链路已通过验证。

参考项目的 Android `FrameProcessor.kt` 将平面访问、均值计算、提示判断和事件发送放在一起；`utils/DataHub.kt` 使用无界队列，数量阈值不是容量限制，消费回调可能在生产线程执行，停止也没有异步消费完成屏障。这些实现不能直接迁入。

`docs/architecture` 的目标架构允许 JS 接收信号批次，并同时描述 Android／iOS。本次以用户确认的边界为准：只实现 Android，采集数据始终留在原生端；实现阶段同步文档，不添加 iOS 或其他来源占位代码。外部行为见本变更的 `native-acquisition` 和 `android-app-foundation` 增量规格。

## Goals / Non-Goals

**Goals:**

- 让像素访问、算法处理、批处理和文件格式拥有可独立修改的边界。
- 让同一完整像素视图支持均值和全帧算法，当前 PPG 与经验提示共享计算而不互相依赖。
- 将高频数据、所有权和停止屏障留在原生侧，JS 仅承担控制和展示。
- 将 `DataHub<T>` 做成可直接复用于其他传感器记录的组件，但用本次 PPG 路径提供真实使用方。

**Non-Goals:**

- 不建立动态插件系统、通用处理图引擎、全局事件总线或公共手写 C++ 层。
- 不实现其他传感器和 iOS，不把将来的类型、空方法或开关当作已完成能力。
- 不实现真实覆盖面积、质量评分、临床有效性或跨传感器时钟同步；本次不生成 `frame.csv` 或 `acc.csv`。
- 不因采用模拟器验收而添加生产伪相机、合成样本或固定成功反馈。

## Decisions

### 1. 采集功能包与宿主配置分离

采集主体放在 `packages/acquisition`。应用通过公开入口控制采集，通过独立的 `acquisition/react` 入口接入原生预览；Nitro 和生成绑定归采集包。Android 源码不散落进 CNG 生成的宿主工程。

建议职责布局如下；Nitro 模板要求的 Gradle、CMake、注册和自动链接文件按实际工具链补齐，不把此布局当成预建空目录清单。

```text
apps/native/src/
|-- app/acquisition.ts
`-- features/acquisition/AcquisitionScreen.tsx

packages/acquisition/
|-- src/
|   |-- client.ts
|   |-- types.ts
|   |-- native/Acquisition.nitro.ts
|   |-- native/CameraPreview.nitro.ts
|   `-- react/CameraPreview.tsx
|-- android/src/main/java/com/healthcvapp/acquisition/
|   |-- bridge/
|   |   |-- HybridAcquisition.kt
|   |   `-- CameraPreviewView.kt
|   |-- session/CaptureSession.kt
|   |-- camera/CameraSource.kt
|   |-- pixels/
|   |   |-- PixelReader.kt
|   |   `-- PixelFrameView.kt
|   |-- processing/
|   |   |-- PixelProcessor.kt
|   |   |-- FramePipeline.kt
|   |   |-- PixelStatisticsExtractor.kt
|   |   |-- PpgRecordProcessor.kt
|   |   `-- CoverageHintProcessor.kt
|   |-- pipeline/DataHub.kt
|   `-- writers/PpgCsvWriter.kt
|-- nitro.json
|-- nitrogen/generated/
`-- package.json
```

相机权限和应用级定制通过 Expo 配置／插件表达。继续使用已锁定的 React、React Native 和 Nitro，不引入第二份运行时；Nitrogen 需与 Nitro 0.37.1 匹配。CameraX 和生成工具的具体依赖补入锁文件，并在现有 Android 工具链上共同构建，不以 TypeScript 可解析代替原生链接验证。

替代方案是把采集直接写入 `apps/native/android`，但 CNG 重建容易丢失代码；或者先拆出独立协议包，但当前没有第二个使用方，不采用。

### 2. JS 使用门面，原生会话拥有运行状态

`AcquisitionClient` 隐藏 Nitro，提供异步的打开、开始、停止和关闭命令，以及类型明确的状态、提示和错误订阅。停止成功返回完成产物；不公开像素、记录列表、信号批次或共享缓冲接口。

`CaptureSession` 负责串行化状态修改和相机／流水线／队列／写入器的生命周期。状态只描述必要的关闭、打开中、预览、采集中、收尾、关闭中和失败等设备事实，不建立每个状态一个类的通用状态引擎。操作进行中不允许建立交叠会话；重复停止可以等待同一收尾结果，不重复写尾批。

`app/acquisition.ts` 独立组装采集依赖，将原生低频通知投影到只读 Nano Stores。页面直接使用现有 React 绑定显示状态并发命令，不复制设备状态机。保留已有认证初始化，但采集不等待它、不要求它成功，也不因云端环境变量缺失而不可用。

原生预览组件只挂接同一个相机会话的预览 Surface，支持标准 `style`，挂载组件不自动打开设备。采集控制不依赖预览事件或页面定时器推进。

替代方案是让页面控制相机生命周期、收集样本再保存，或让 JS 维护第二套运行状态；两者都会重新引入旧项目的时序与缓存问题，不采用。

### 3. 像素读取采用只读借用视图

`CameraSource` 负责后摄、CameraX 用例、实际格式和帧来源，不计算 PPG。`PixelReader` 适配实际的 `YUV_420_888` 平面，提供逻辑 Y/U/V 通道视图；每个通道包含缓冲区、基址偏移、有效尺寸、字节行步长和字节像素步长，不能假定平面连续或色度平面互不共享底层存储。

`PixelFrameView` 同时携带宽高、有效裁剪区域、旋转／镜像信息、可取得的颜色信息、会话标识、帧序号及时间。处理器能访问全部有效像素，不以 `number[]` 或仅有均值的结构替代帧。

默认不复制整帧，不先旋转图像，不统一转换成 RGB；几何和布局信息保留为元数据。后续确有连续 RGB 输入要求时，只为相应算法执行必要转换。

`FramePipeline` 拥有每帧处理作用域：处理器只读借用，不保存引用、不修改缓冲、不自行释放；作用域正常或异常结束时，由平台适配统一关闭 `ImageProxy`。关闭前所有本帧同步处理必须结束。文件队列只接收独立的数值记录，不持有原生帧。

替代方案是先生成统一 RGB 大数组，再分派给处理器，但会增加当前路径不需要的转换、复制和内存压力，不采用。

### 4. 处理器组合与共享统计分开

处理器通过 `PixelProcessor` 契约访问当前帧及可用的共享统计，并连接各自类型明确的原生输出入口。`FramePipeline` 组合当前实际启用的处理器，不使用万能事件字典或动态注册系统。

当前执行顺序为：建立像素视图；`PixelStatisticsExtractor` 一次遍历有效图像计算全帧 Y/U/V 统计；`PpgRecordProcessor` 形成记录；`CoverageHintProcessor` 根据相同统计生成提示。这里的独立是职责独立，不要求每个处理器重复遍历或单独分配线程。

统计使用原生数值累加，不创建逐像素对象，不在像素循环中通过 JS 或通用逐像素回调调用算法。均值按实际有效通道样本数计算，考虑裁剪、平面步长和色度采样，不机械复制旧实现的整除分块循环。

完整像素仍可被后续处理器直接读取；共享统计不是所有算法的强制输入。当前只计算这两个处理器实际需要的统计，不提前增加网格、直方图、特征缓存或空的全帧处理器。

替代方案是让覆盖处理器依赖 PPG 处理器输出，或按责任链先求平均再分发。前者耦合不同输出，后者丢失空间信息，均不采用。

### 5. PPG 字段兼容与经验提示语义

本次每个实际交付且处于采集窗口内的帧形成一个全帧块，`blockIndex=0`。CSV 表头及时间取值沿用旧 Android：

| 字段 | 含义 |
| --- | --- |
| `timestamp` | 处理该帧时读取的 `SystemClock.elapsedRealtimeNanos()`，换算为毫秒；不是曝光发生时间 |
| `timestampFrame` | 图像原始采集时间戳，纳秒换算为毫秒；不改用 JS 到达时间 |
| `timestampSystem` | `System.nanoTime()` 换算为毫秒；不是 Unix 时间 |
| `avgY`、`avgU`、`avgV` | 有效图像区域的三个原始通道均值 |
| `frameIndex` | 本次正式采集内从 0 开始的交付帧序号，不证明相机无跳帧 |
| `blockIndex` | 本次固定为 0 |

时间保留毫秒小数，不额外截断为整数。请求 FPS 与实际交付时间分开，不能把递增序号当作完整性证明。正式采集前的在途帧通过会话代次和采集起点的单调接收边界排除，不只根据 JS 收到通知时的状态接收整个批次。

提示沿用参考代码的计算：由均值推导 `r/g/b`，系数依次为 `r=Y+1.5748*(V-128)`、`g=Y-0.1873*(U-128)-0.4681*(V-128)`、`b=Y+1.8556*(U-128)`；和大于 0 时归一化，否则比例取 0。`showSurroundingTip` 使用 `avgY<25`；`showCoveringTip` 使用红色比例不大于 0.5、绿色比例不小于 0.2 或蓝色比例不小于 0.2 的任一条件。

这些是未经本项目真机验证的经验提示，不是逐像素 RGB 输出、真实覆盖面积或质量门禁。取得有效统计前为未评估；只合并最新状态或在变化时通知，不等待 DataHub 消费，不暂停或延长采集。

替代方案是立即设计新的空间覆盖算法，但会扩大本次目标且需要真机标定，不采用。

### 6. DataHub 是所有采集源共用的有界批处理组件

`DataHub<T>` 位于原生 `pipeline`，不属于相机或 PPG 处理器。后续加速度、陀螺仪等记录可以复用同一实现；每个数据流／会话有独立实例，不使用混合类型的全局单例。本次只有 `DataHub<PpgRecord>` 的生产使用方，不创建其他传感器空实现。

队列契约包括：

- 生产端短操作入队，明确区分已接收、容量不足、已关闭和消费失败；达到数量阈值只唤醒消费者，不能在相机线程调用文件写入。
- 缓冲容量、最大批次大小、消费间隔分别配置。初始实现参数取容量 256 条、最大批次 50 条、间隔 1000 ms；后两项参考旧实现，容量是新增硬上限。这些值可调整，不构成 FPS 或持久化延迟保证。
- 容量占用包含待分批记录、已组批及正在消费但尚未完成的记录，成功完成消费后才释放对应额度。不能使用累计采样计数或只看底层队列长度。
- 使用固定容量存储和一个后台消费者，数量／时间触发统一调度，保持顺序且不重复、不并发调用消费者；不为每次入队创建新任务。
- 消费接口必须能够等待实际消费完成，不把启动异步任务后立即返回视为完成。批次交给消费者后，在其结束前不得复用或覆盖批次存储；减少不必要的对象和列表复制。
- 容量不足不阻塞相机等待磁盘、不覆盖记录、不无限扩容，由会话报告失败并收尾。消费者异常记录为终态错误，关闭入口并唤醒等待者，不静默重试。
- 正常关闭拒绝新记录，停止定时触发，顺序完成所有已接收数据和尾批，等待在途消费结束。错误终止和正常排空不同，错误不得产生正常完成结果。
- 不保留旧 `DataHub<T,U>` 的共享可变 `meta`。帧身份和时间属于记录；会话固定信息由消费者的会话上下文持有。反馈状态不进入记录写入队列。

`CaptureSession` 持有队列及其子任务生命周期，停止时先排空再取消所属任务，避免取消作用域导致尾批丢失。队列接受调用方提供的消费执行上下文，文件消费者使用原生 I/O 后台上下文，不硬编码相机或 JS 线程。

替代方案是直接复用旧无界队列，或让所有传感器共享一个实例。前者没有真实背压和消费屏障，后者会混淆容量、类型与结束条件，不采用。

### 7. 写入器不承担队列调度

`PpgCsvWriter` 只负责创建文件、写表头、编码记录、批量写入、刷新和关闭；没有自己的定时器、队列或第二个消费者。正常路径由 DataHub 的串行消费回调调用它。

文件路径使用应用私有持久目录下的会话独立目录，例如 `filesDir/acquisition/<sessionId>/ppg.csv`，避免固定文件名跨会话覆盖。文件路径与将来的上传 URI 是不同概念，本次不引入上传适配。

只有正常关闭后才建立完成产物，包含会话标识、文件系统路径及大小等低频信息。失败时确保关闭句柄和释放运行资源，但不把部分文件返回为成功，也不增加补样、自动恢复或保留期清理功能。正常关闭相机、重新打开或离开页面不删除已经完成的文件。

替代方案是让 DataHub 知道 CSV 或让写入器再加一层队列，会分别损害复用和停止语义，不采用。

### 8. 正常停止、关闭与中断使用同一收尾边界

正常停止先关闭本次记录入口并固定会话代次，再等待已进入处理作用域的帧结束；随后关闭并等待 DataHub 排空，最后刷新并关闭文件。只有这些步骤成功后才通知产物完成。预览可继续，下一次开始需创建新的队列、写入器和会话路径。

关闭相机时，若正在采集，先执行上述正常停止并保留完成产物，再解绑 CameraX、释放预览与处理资源。重复关闭不重复释放，也不删除文件。界面卸载由应用采集组装层调用关闭，不把异步收尾实现散落到页面。

队列满、像素处理失败、写入失败、设备中断或应用进入后台时，终止当前采集的成功路径并释放资源，不自动后台采集或恢复。最终错误携带会话身份；旧代次的迟到像素和通知不能进入新会话。原生帧释放始终执行，不因某个处理器失败而遗漏。

替代方案是先发停止通知再异步 flush，或先取消任务再尝试清队列，会允许不完整文件被报告为成功，不采用。

### 9. 背压与性能不靠线程数量解决

CameraX 使用独立原生串行分析执行器，图像分析先采用旧路径的 `STRATEGY_BLOCK_PRODUCER` 和 CameraX 默认有限图像队列，不增大图像队列掩盖持续超载。它可能连同预览一起受阻，因此不承诺目标帧率；不能将其描述为永不丢帧。

默认候选请求沿用旧项目的 720×720／30 FPS，通过能力查询和 CameraX 支持的协商方式选择实际组合；报告实际尺寸和可用能力，不把请求值冒充实测。自动曝光作为初始方案；后摄支持 torch 时按打开状态使用，不支持时明确能力而不伪造成功。模拟器后摄输入由 AVD 提供，不能因此在采集模块中回退为合成数据。

当前帧处理仅一次像素遍历加少量提示计算；PPG 记录入队后尽快释放帧，磁盘 I/O 不占分析线程。反馈降频不改变已接收记录的保存。没有当前需求时不引入逐帧并行任务、GPU 或共享 C++ 处理层。

选择 `KEEP_ONLY_LATEST` 可以降低分析积压，但会主动跳过未处理帧；本次不以该方式隐藏 PPG 缺口。用户后续可在真机上比较处理耗时、采集时间间隔、预览、内存和发热，但这些不构成本次模拟器验收门槛。

### 10. 模拟器验收与正确性验证分层

端到端验收使用当前 Android development build，在具备后摄输入的模拟器中真实操作打开、开始、停止，检查停止返回路径在应用私有目录中存在，可通过应用低频文件查询或 `adb shell run-as com.healthcvapp.mobile` 核实。不请求云端、不使用 JS 造样本替代 CameraX。

文件存在是用户指定的产物检查下限；不额外要求非空、固定行数、字段数值比对或稳定 FPS 作为本次端到端验收门槛。模拟器没有物理手指和真实 PPG，不能据其提示判断医学或覆盖准确性。不得用只调用文件创建方法、原生模块名称可解析或 mock 相机代替实际页面链路。

实现中的必要行为测试只覆盖明确风险：不同 stride／裁剪布局下的像素读取、共享统计与经验提示边界、DataHub 容量／顺序／并发触发／异步排空／消费失败，以及会话迟到回调或写入失败不交付成功产物。不为导出名称、字段转发、默认参数或源码文本建立测试；当前 Native 与 cloud-client 已有测试保持兼容。

验证记录放在 `docs/development`，协议说明放在 `docs/acquisition`；说明模拟器设备、实际命令、操作结果和文件存在证据，明确真机由用户后续自行验证，不创建必须勾选的真机任务。当前没有实现或验证结果。

## Risks / Trade-offs

- [模拟器后摄缺失或输入配置不正确] → 先配置 AVD 的后置虚拟场景／主机摄像头，记录实际来源；没有帧时修复模拟器配置，不增加生产合成回退，也不将仅表头文件宣称为传感器正确。
- [均值提示不具备空间覆盖语义] → 名称和界面只表达经验操作提示；保留完整像素输入供以后独立算法使用，不报告面积百分比或质量通过。
- [BLOCK_PRODUCER 在持续过慢时影响预览] → 控制当前处理量、分离磁盘 I/O，保持图像与记录队列有界；真机性能留给用户后续评估，不用扩容或静默跳过掩盖问题。
- [原生帧被释放后仍被使用] → 明确只读借用作用域，所有同步处理结束后统一释放；异步队列只持有数值记录。
- [数据已出队但仍在写入导致容量被低估] → 消费完成后才释放容量额度，使用慢消费者场景验证排空与容量。
- [旧时间字段同名但并非墙钟或已同步时间] → 文档逐列记录旧 Android 含义；本次不做跨源对齐，也不改变字段名制造虚假的统一时间协议。

## Migration Plan

1. 新增采集包及其 Android 原生接入，通过配置／插件纳入 CNG，保持现有认证和云端包不变。
2. 接通真实像素、共享处理、公共 DataHub 和文件消费者，再将应用默认界面切换为采集验证界面；不交付只有空接口的中间状态。
3. 在 Android 模拟器完成实际页面和文件存在检查，更新已执行的验证记录与长期架构／协议说明。
4. 若实现需要回退，恢复应用入口和采集模块依赖／配置的变更，不通过撤销实现删除用户已完成的文件。本次没有服务端部署或数据迁移。
