# Design

## Context

动机与本次范围见 `proposal.md`，外部契约见 `specs/android-passive-capture/spec.md`。本变更跨越原生服务、权限、系统通知、相机生命周期和应用入口，涉及新的录像依赖及用户隐私，因此需要技术设计。

当前实现与约束：

- `apps/native/App.tsx` 挂载主动 `AcquisitionScreen`。`app/acquisition.ts` 在页面卸载时调用主动 `closeCamera()`；不能把该清理接到被动服务上。
- 原有 `AcquisitionService` 是依赖 `ReactContext` 的普通 Kotlin 类，并不是 Android Service。其打开过程需要 `PreviewView` 和 Activity，`CameraSource` 固定后摄、预览与 YUV 分析，并在页面 `ON_STOP` 时中断。
- 原有 Nitro 契约只描述主动 PPG、提示和双 CSV；`DataHub<CaptureRecord>` 承载数值记录，不是视频编码或帧缓存接口。
- 当前 CameraX 组件为 1.6.2，没有 `camera-video`；宿主显式配置的运行权限只有 `CAMERA`。已有内部测试 Release 构建脚本，可用于不依赖 Metro 的真机验证。
- 本轮只读设备观察为 PPG-AN00、API 36，安装包 `targetSdk=36`；相机已授权，未声明相机前台服务权限，服务查询为空。这不是新后台路径的实测证据。
- 已有 `native-acquisition` 的模拟器验收边界只属于主动 PPG，本变更不能沿用它来免除实体手机后台验证。

## Goals / Non-Goals

**Goals:**

- 让权限与用户启用产生一个真实的、可关闭的原生运行期，而不是持久化一个假定常驻的布尔值。
- 将解锁与周期策略同视频输出分开，让未来像素序列或人脸筛选不要求重写触发规则。
- 以无页面、无预览、相机间歇释放的方式验证后台重新打开摄像头，并保留可解码产物和可追溯结果。

**Non-Goals:**

- 不为未来像素路径预建插件、空处理器或统一帧事件总线，不为录像运行 `ImageAnalysis`。
- 不设计主动优先级、自动抢占或并行双摄；仅用必要的占用保护防止两个入口误碰同一资源。
- 不添加上传、帐号绑定、视频自动清理、机主识别、设备管理权限、后台弹窗或永久保活机制。

## Decisions

### 1. 原生 Service 拥有运行期，JS 只负责用户控制和低频展示

在 `packages/acquisition` 内新增独立的被动控制契约及 Kotlin 实现，使用单独 Nitro 控制对象／客户端入口，不扩充主动 `AcquisitionState` 来同时表达两条业务。服务和录像组件使用应用 Context；ReactContext 只存在于控制桥接，不拥有服务实例或录像任务。

职责按边界放入被动采集子目录：启停与快照、Android 前台服务与通知、解锁周期判断、前摄录像、完成文件查询。具体类名服从实现时的现有命名，不预建无使用方的模块。

Android Service 持有 CameraX 所需的服务生命周期，不能传入页面 Activity，不能沿用主动相机的 `ON_STOP` 中断观察。可使用 `LifecycleService` 并按需添加 lifecycle-service 依赖。服务存活期间在原生注册解锁和屏幕关闭事件；屏幕关闭立即终止当前尝试，打开前及录制状态核对时再检查锁屏状态。注册、注销、停止和配置更新都在原生串行控制边界中执行。

JS 门面仅提供配置、启用、关闭、真实状态、最近一次触发／跳过／失败原因及产物引用。页面不挂载预览，不接收视频字节、图像帧或逐帧通知；页面清理只解除被动状态订阅。

替代方案是 Headless JS 或页面定时器触发录像，但它们把成功依赖放回 JS／页面存活，无法提供本次所需的平台证据，不采用。

### 2. 用户可见时完成授权并启动 camera 类型前台服务

启用顺序为：解释用途与保存内容，验证配置；用户点击“授权并启用无扰采集”时，先显示厂商后台活动设置说明和应用设置入口，用户确认已完成或此设备不适用后，再请求相机权限、Android 13 以上通知权限；检查应用通知和专用渠道；用户在可见页面明确启用时启动服务，服务及时进入前台并回报真实等待状态。创建客户端、首次进入界面和启用完成均不打开相机，直到之后的新解锁事件。

声明 `FOREGROUND_SERVICE`、Android 14 以上的 `FOREGROUND_SERVICE_CAMERA` 及 `foregroundServiceType="camera"`；不以健康用途改报 `health` 类型。服务保持非导出。库侧服务声明放在库 manifest，宿主权限和通知相关配置通过 `app.json`／必要的 Expo config plugin 表达，保证 CNG 重建后仍存在。用户运行时授权不通过 ADB 代授。

通知可见性是本产品启用条件，而不是 Android 对所有前台服务的硬性规定。运行中至少在每次解锁处理和界面重新核对时检查必要条件；发现撤销后停止功能并给出可判别原因。厂商后台／电池设置只在被动采集启用操作时提供与实测设备对应的人工说明和应用设置入口；应用不自动授予或宣称已检测该设置，不请求 Doze 豁免、悬浮窗、精确闹钟、麦克风、共享存储或设备管理员权限来绕过限制。

替代方案是等到解锁广播后才从后台新建服务，但相机 while-in-use 限制使该路径不能成为通用前提，不采用。

### 3. 一条安静通知展示服务事实，明确提供关闭

创建专用、低重要性且无声音／振动的通知渠道；同一通知 ID 更新等待和录像状态，设置 ongoing 和 only-alert-once，不把每次状态变化变成新提醒。

- 等待：“无扰式采集已启用”，说明等待符合周期的解锁事件；此时相机关闭。
- 录像：“无扰式采集进行中”，说明前摄正在录制。
- 操作：“关闭无扰采集”，由明确、不可变且指向本应用的 PendingIntent 进入原生关闭流程，不依赖 JS 执行。
- 正文点击只进入功能状态入口，不自动开相机或开始主动 PPG。

Android 14 起 ongoing 通知可被用户单独划除。单独划除不等价于关闭服务，不反复重发通知阻止清除；保留 App 内真实状态与关闭入口，以及系统活动应用的控制。若通知权限或渠道被禁用，则按启用条件失效处理，而不是混同为单次划除。停止功能完成后移除服务通知；无法继续运行时不保留虚假的正常等待通知。

### 4. 触发是解锁事件与周期门槛，不是周期任务

使用运行中服务动态接收的 `ACTION_USER_PRESENT` 作为候选，不能辨别解锁方式。收到事件后先核对功能、权限与锁屏状态，再判断是否已有启动／录像／收尾和周期是否满足；不检查 React AppState 来决定资格，不设置解锁后延迟。

本提案的默认参数及时间语义如下，属于实现前可评审的设计选择，而不是用户已经指定的固定参数：

| 项目 | 提案默认 |
| --- | --- |
| 周期 | 7200 秒，可在未启用时配置 |
| 单次目标录像时长 | 10 秒，可在未启用时配置 |
| 首次触发 | 本次启用运行后的第一个有效解锁事件即可尝试 |
| 周期起点 | 最近一次 `VideoRecordEvent.Start` 到达时的单调时间 |
| 时长起点 | 同一次实际录像开始事件，不包含相机打开耗时 |
| 周期已到但未解锁 | 不开摄像头，继续等待 |

配置为有限正数，不能用非法数值启动；运行期间显示本次生效配置，修改需先关闭再重新启用，避免同一会话内计时语义变化。周期判断用 `elapsedRealtime`，不依赖墙上日期。开始后中断仍计入周期；未实际开始则不更新周期，但也不在同一次事件中自动重试。重复事件、忙状态和收尾期间的事件直接跳过，没有积压、补采或定时重试。

周期状态只属于当前原生启用运行；本次不实现跨进程／跨重启调度恢复，重新明确启用会建立新的运行期。

### 5. 当前仅使用无预览 VideoCapture，不经过 PPG 管线

加入同版本 CameraX `camera-video:1.6.2`，使用前摄 `VideoCapture<Recorder>`，不绑定 `Preview` 或 `ImageAnalysis`。输出选用 MP4，优先请求设备支持的 HD，允许按实际能力选择较低支持档，返回真实媒体尺寸；不承诺原始 YUV、无损编码、固定 720×720 或稳定 30 FPS。录制不启用音频、torch、美颜、数字变焦或人脸裁剪。

原生收到录像开始事件后控制目标时长并调用停止，等待 Finalize 和设备释放后才回到等待。避免在 JS 中以 `setTimeout` 计算录像长度。打开和收尾需要有界等待，超时按失败释放，不通过无限等待维持“录制中”。

可视内容不作为保存门槛：黑暗、没有人脸或人脸偏离都不调用算法过滤。视频保存成功仅说明文件正常完成，不能表示 rPPG 有效。

未来切换像素序列时，只替换具体采集输出及其会话产物；是否做人脸筛选仍需另行确定。若未来仍录像并同时分析人脸，需要重新验证 `VideoCapture + ImageAnalysis` 的设备组合能力。本次不提前开启分析用例，也不把视频解码成像素当作未来唯一扩展接口。

### 6. 会话终态与资源所有权独立，保留最小占用保护

服务采用简单的未启用、启动服务、等待、打开录像、录像中、收尾、关闭和失败事实，不引入通用状态机库。每次启用有运行代次，每段录像有独立会话 ID；事件、定时停止和 Finalize 回调都核对所属代次及会话。

关闭功能先关闭事件入口和取消待执行命令，再终止录制并等待收尾／设备释放，最后移除通知和停止服务。重新锁屏、权限失效或用户中途关闭的片段不作为目标时长完成产物；迟到回调不能发布成功、恢复功能或释放新会话资源。错误处理中仍需执行统一释放。

主动 PPG 的生命周期、数值管线和产物不改。两个入口仅共享一个很小的相机使用权保护，打开前取得、关闭或打开失败后按持有者释放；被占用则返回忙／跳过，不抢占、不自动切摄像头、不排队。该保护不按应用前后台划分模式，也不定义复杂的主动／被动优先级。主动页面的卸载只关闭它持有的主动相机，不能直接停止被动服务。

### 7. 视频按私有持久目录发布，完成与未完成区分

每段输出到 `filesDir/passive-capture/<sessionId>/video.mp4.part`。只有正常时长结束、Finalize 成功、媒体可读取且文件存在后，提升为 `video.mp4` 并发布完成引用；错误、取消、截短或进程中断遗留的临时文件不进入完成列表。

产物字段只包含当前需要的会话 ID、最终路径、字节数、实际媒体时长和尺寸；时间字段需明确单调时间或文件时间语义，不能互相冒充。应用按需查询专用目录中的最终 MP4 并读取媒体信息，以便进程重开后仍能查看完成产物；不依赖内存列表或新增数据库。

每个会话只写自身路径，不覆盖已完成视频。关闭页面、服务和应用不删除产物。本次没有自动清理或上传；私有持久文件会占用存储，验证文档需说明这一边界。设备内媒体读取用于确认存在有效视频轨和时长，完整解码检查留给真机验收。

### 8. 不自动恢复服务，避免把偏好当成运行事实

服务使用非自动恢复语义，不实现开机广播拉起、START_STICKY 自动录像或异常后自行复活。用户从系统停止应用、进程死亡或重启后，需要重新进入并明确启用。可以保存上次配置，但不能以保存的“已启用”标记声称服务仍活着。重新进入界面时从原生真实状态重新同步；完成文件查询独立于服务是否运行。

### 9. 先证明真实后台路径，再完成回归与验证记录

使用包含 JS bundle 的内部测试 Release APK，在真机上通过页面完成授权启用；不依赖 Metro、ADB 代授权、后台弹出 Activity 或隐藏预览作为成功条件。现有 development build 可辅助诊断，但不是最终后台证明。

先用短周期和真实锁屏解锁检查重复触发、周期内抑制、通知停止、权限拒绝／撤销、重新锁屏及相机忙；然后以目标周期实际待机，完成第二次成功录像并证明等待期间没有相机占用。默认 2 小时的目标周期验证必须真实跨越该间隔，不能改成几秒再声称通过。

每次证据至少关联运行／会话、解锁接收、开始尝试、实际 Start、停止原因、Finalize、释放及产物路径；仅保留低频控制事件和错误，不记录帧、令牌或人员身份。用媒体探测和完整解码检查实际时长、前摄画面、视频轨和无音轨；目标时长允许编码及停止收尾导致的有限偏差，先以正负 1 秒作为验收容差，记录真实值，不修改元数据凑时长。

按现有 Kotlin JUnit／coroutines-test 约定，为周期边界、开始失败与中断计时、事件重入、关闭与迟到完成、文件发布失败写必要行为测试。权限系统、通知栏、服务存活和相机是否可开必须由真机行为证明，不能用 mock 回调回显代替。

## Risks / Trade-offs

- [后台服务允许启动不等于锁屏后一定能重新打开相机] → 将“提前可见启动服务、关闭相机等待、解锁重开”作为最先执行的真机路径；失败时保留系统错误，不通过一直占用相机或后台弹页面改变问题。
- [厂商省电策略或用户停止导致服务消失] → 记录默认设置与必要的用户设置，展示真实未运行状态；不承诺全厂商常驻，不自动绕过停止。
- [持续通知可被划除或权限被撤销] → 分清通知单独清除、权限／渠道禁用和系统停止；产品只在检查到必要条件可用时接受新录像。
- [相机打开耗时使画面错过用户正脸] → 记录解锁到 Start 的真实延迟，不在本次用人脸算法或延迟假设掩盖；数据价值留给后续云端验证。
- [编码视频不能等同原始像素，压缩可能影响后续 rPPG] → 明确当前只验证后台通路和可解码产物，长期数据表示另行决策。
- [长期保存完整前摄画面有隐私和存储成本] → 明确用户授权、无音频、应用私有目录、可关闭和无上传；不把验证版描述成已具备生产留存策略。
- [真机可行性失败] → 输出清楚的设备级否定结论和失败阶段，不将功能验收勾为通过；若公开 API 无法满足，需用户重新决定目标范围，不能偷换成前台手动录像。

## Migration Plan

1. 在既有采集包内新增被动功能及独立页面控制，不迁移已有 PPG 文件、不改变其公开命令语义。
2. 通过 Expo 源配置维护声明，先执行无预览后台真机路径，再完成周边边界与主动 PPG 回归。
3. 证据通过后更新 `docs/acquisition` 的被动协议、`docs/development` 的真机步骤与结果及受影响的架构说明。
4. 若需回退，用户先关闭被动服务，再撤回本次新增入口、服务和依赖；保留用户已有 PPG 及已完成视频，不删除存量产物。

## Open Questions

- 长期选择视频还是像素序列、是否增加人脸画面筛选，均明确留到后续变更；不会阻塞本次直接录像与后台路径验证。
- 后续云端输入格式、上传与留存策略尚未定义，本次不假定当前 PPG 示例接口支持前摄视频。
