# server-query-lifecycle Specification

## Purpose

为应用已有的认证门控服务端资源提供明确的新鲜期、回收和原生生命周期刷新行为，使调用方能够复用缓存、区分首次加载与刷新失败，并确保网络恢复或语言变化不会重复提交业务操作或破坏账号隔离。

## Requirements

### Requirement: 查询新鲜期按资源语义确定
应用 MUST 对本人资料使用1分钟、模型目录30分钟、任务列表与健康最新结果及历史区间30秒的新鲜期。任务详情在 SUCCEEDED 或 FAILED 时 MUST 使用5分钟新鲜期，其他或未知状态 MUST 使用0。新鲜期 MUST 不等同自动轮询间隔或删除时间，状态变化后 MUST 按最新响应重新确定策略。

#### Scenario: 新鲜资料重复读取
- **WHEN** 同一会话在1分钟内重复读取已成功缓存且未主动失效的本人资料
- **THEN** 可复用缓存而不无故重复请求，主动刷新仍可请求最新数据

#### Scenario: 活动任务进入失败终态
- **WHEN** 任务详情从 RUNNING 更新为 FAILED
- **THEN** 之后按终态的5分钟新鲜期复用详情，不将任务失败误当作查询通信失败

#### Scenario: 服务端引入未知状态
- **WHEN** 任务详情返回尚未识别的状态值
- **THEN** 保留原始状态并采用0新鲜期，不自行判断成功、失败或启动轮询

#### Scenario: 健康记录正常刷新
- **WHEN** 用户下拉首页、新有效结果使首页查询键失效，或历史按既定规则触发读取
- **THEN** 首页在首次无缓存或上述显式触发时读取最新结果，不因返回、聚焦、非首次进入、应用回前台、网络恢复或仅缓存过期自动重取；历史首次进入及每次导航重新聚焦仍读取，筛选变化从第一页建立新轮，不只替换旧区间第一页。页面按已确认加载／刷新状态反馈，不增加常驻刷新按钮或分页技术说明

### Requirement: 无观察者缓存有界回收且不持久化

服务端资源缓存 MUST 仅保存在内存，无观察者时 MUST 以 10 分钟为回收基线；重新观察 MUST 结束该次无观察者等待。缓存回收 MUST 不删除采集文件、清除语言偏好或判定认证失效，进程重启 MUST 不把偏好存储当作服务端缓存恢复源。

#### Scenario: 缓存回收不触及产物
- **WHEN** 无观察者资源达到回收期限且本地已有完成 CSV 或视频
- **THEN** 对应缓存可被回收，但产物和语言偏好仍保留，认证状态不因此变化

### Requirement: 前台和网络恢复只刷新允许的查询
应用 MUST 统一反映宿主前后台与网络可用性；返回前台或网络恢复时，只有已启用、允许自动刷新且已过期的活动查询可刷新。首次网络状态未知 MUST 不作为已断网的确定事实。该机制 MUST 不自动恢复采集、不自行启动任务轮询、不重放写操作或被取消的旧会话请求；可见任务的轮询仅由显式业务观察控制。

#### Scenario: 返回前台刷新已过期资料
- **WHEN** 当前已认证会话仍观察资料查询，资料已过期，应用从后台返回且网络可用
- **THEN** 触发允许的资料刷新，新鲜模型目录不因此重新请求；没有观察者的查询不因该事件全部加载

#### Scenario: 网络恢复不重放提交
- **WHEN** 一次写操作因离线或结果未知结束，随后网络恢复
- **THEN** 不自动重试创建、上传提交、资料修改或其他写操作，用户或业务会话仍需按原操作协议决定下一步

#### Scenario: 可见业务任务恢复查询
- **WHEN** 当前有效业务页面回到前台，仍观察 SUBMITTED 或 RUNNING 任务
- **THEN** 可先读取真实详情，再按业务观察规则安排后续查询；不因此恢复已取消的上传或采集

### Requirement: 查询刷新失败保留已确认数据

查询已有成功数据时，后续刷新失败 MUST 保留旧数据及最后成功时间，消费者 MUST 能区分刷新失败和首次加载失败；MUST 不用空列表、零值或成功状态覆盖失败。通用查询和变更 MUST 不自动重试，不自动做乐观成功。

#### Scenario: 有缓存的历史刷新失败
- **WHEN** 历史查询已有记录，刷新遇到网络错误
- **THEN** 消费者仍可读取旧记录并识别刷新错误，不将该结果表达为无记录或首次加载空屏

### Requirement: 参数与身份共同隔离查询
查询 MUST 沿用服务地址、渠道和会话代次隔离，并包含实际请求的资源标识及支持的筛选、排序和分页参数。健康历史完整区间 MUST 包含指标与起止日期，页面加载轮次 MUST 隔离新旧响应。语言只影响展示且响应本身不变时 MUST 不产生第二份缓存。退出或换号 MUST 取消旧请求、清理旧缓存并阻断迟到回写，不清除非认证偏好。

#### Scenario: 分页切换和语言变化
- **WHEN** 用户先切换任务列表分页，随后仅改变展示语言
- **THEN** 不同分页使用不同缓存身份，而同一分页不因语言产生重复数据缓存

#### Scenario: 账号切换时旧响应迟到
- **WHEN** 旧会话查询尚未返回就退出或登录另一账号，之后旧响应到达
- **THEN** 旧响应不能重新填充当前或已清理的旧会话资源，当前身份无法读取旧账号数据，非认证偏好保留

#### Scenario: 历史筛选切换后旧页返回
- **WHEN** 用户切换指标或日期区间，旧区间后续页才返回
- **THEN** 不将旧页合入新区间，不改变当前区间完整性、记录、趋势或统计

### Requirement: 健康区间按完整加载轮次刷新
健康历史 MUST 将同一筛选区间的分页归为同一加载轮次，完整加载后才发布本轮最终趋势、统计及完整记录。任一页失败 MUST 保留内部未完成和错误，而非空页结束；已有同区间完整缓存可保留，但页面加载或失败时不继续展示旧内容，不能把失败轮次部分页作为成功结果。已知新有效测量、total改变或重复recordId时 MUST 丢弃该轮整段刷新，不混用旧页或宣称去重保证快照完整性；持续变化等待再次进入、显式重新获取或切换筛选，不无界重取，不展示完成度。

#### Scenario: 后续页失败
- **WHEN** 已取得第一页但第二页读取失败
- **THEN** 保留未完成及错误，不输出失败轮次的最终统计；页面统一显示获取失败及重新获取，不使用 Toast 或继续展示旧完整内容。再次进入、重新获取或切换筛选从第一页建立新轮次

#### Scenario: 加载中发现集合变化
- **WHEN** total 改变或遇到重复 recordId
- **THEN** 丢弃该轮全部页；可见在线时允许一次整段新读取，持续变化保持内部未完成，等待再次进入、显式重新获取或筛选变化，不循环拉取或增加常驻刷新入口

### Requirement: 有效任务完成失效健康资源而不拼接本地读数
当前业务任务完成并产生有效成员时，应用 MUST 失效该会话最新健康结果和已缓存历史区间，按各自查询协议读取权威记录，不直接以本地采集或报告对象追加历史。当前代次已有的 latest 查询缓存 MUST 在失效时重新读取，不论是否存在活动观察者或首页是否可见，不依赖返回或聚焦首页触发；尚未缓存时仍由首次进入读取。失败或 ALL_FAILED MUST 不用空值覆盖此前有效结果；清理缓存仍 MUST 不删除采集文件。

#### Scenario: PPG 部分成功
- **WHEN** 当前场景部分成员成功
- **THEN** 最新结果和相关历史区间通过服务端重新读取；成功指标可更新，失败指标保留后端此前最新有效记录，不把失败成员值补零

#### Scenario: 首页未展示时产生新有效记录
- **WHEN** 首页最新结果已缓存但当前没有活动观察者，当前代次的任务产生有效成员
- **THEN** 失效并重取该代次对应的 latest 键，缓存更新为服务端最新结果，后续返回首页直接展示该缓存；不请求旧代次或伪造本地读数

### Requirement: 健康查询错误事实与页面保留策略分开
应用 MUST 保留请求失败、成功空数据及刷新中等真实查询状态，不用成功空响应吞掉错误。首页获取或刷新失败后 MUST 以对应Toast反馈并显示空数据，即使查询缓存仍有旧值；历史首次读取及同区间刷新 MUST 共用页面加载，获取或刷新失败共用页面失败及重新获取，不显示旧完整内容、不使用 Toast。更换账号或筛选 MUST 不借用旧作用域内容，后续成功读取才替换对应失败展示。

#### Scenario: 相同请求错误在首页和历史的不同反馈
- **WHEN** 首页最新记录及已有完整内容的历史区间分别刷新失败
- **THEN** 两个查询均保留错误事实且不继续显示旧读数；首页显示空数据及 Toast，历史显示页面失败及重新获取，不使用 Toast，均不产生零值、默认健康结果或失败轮次部分统计

#### Scenario: 显式重新获取不扩大请求范围
- **WHEN** 用户在历史获取失败或任务结果获取失败中点击重新获取
- **THEN** 历史从当前筛选第一页重读，报告重查原taskId；不重建任务、不重传文件、不开始设备采集，也不自动重放写操作
