# 产品需求与功能范围

> 文档状态：产品需求基线。本文记录已确认的产品决策、功能范围和当前缺失的契约；未确认内容明确列在“待补充的产品要求”中。本文不表示对应算法或用户功能已经实现。

## 1. 产品定位

- 目标用户：进行个人日常健康管理的普通用户。
- 产品按健康指标组织功能，不按相机、传感器、文件等实现方式组织用户功能。
- 已明确的目标指标为血压、心率、呼吸率和血氧饱和度。其他指标须单独确认后再加入范围。
- 产品提供个人测量记录和规则评估，不提供临床诊断或个性化健康建议。

## 2. 已确认的产品决策

| 决策 | 已确认内容 |
| --- | --- |
| 测量任务 | 每项指标分别发起任务，分别保留状态、结果和历史。 |
| 指标范围 | 四项指标都是产品目标；各项达到算法契约和验证条件后逐项开放。 |
| 结果内容 | 展示读数、单位、测量时间、质量信息、参考范围和评估状态。 |
| 评估位置 | 客户端使用版本化规则计算评估状态和参考范围。 |
| 规则适用性 | 每项指标的验证契约声明适用人群及所需资料；用户不适用或必要资料缺失时，不给出评估状态。 |
| 历史评估 | 历史读数按当前规则重新评估；原始读数和测量时间保持不变，并标明规则版本与评估时间。 |
| 健康建议 | 当前范围不包含个性化建议或诊断结论。 |

规则更新可能改变同一条历史读数的评估状态。历史页必须表达当前评估所使用的规则版本和时间，不得让用户误以为原始测量值发生变化。

## 3. 产品功能范围

### 3.1 账号与健康资料

- 支持用户注册、登录、退出，以及本人资料查看和更新。
- 评估只使用对应指标契约明确要求的资料字段；不因某项测量而默认要求填写全部健康资料。
- 对有明确语义的未知、未填写和“否”分别处理，不相互替代。

### 3.2 指标目录与独立测量

- 用户功能以血压、心率、呼吸率、血氧饱和度等指标为入口。
- 一次任务以一个指标为主要目标；不得把多种测量默认为同一项，也不得仅凭共同采集信号推定其他指标已得到结果。
- 每项指标单独维护是否可用。只有该项的结果契约、质量信息、适用范围、评估规则和验证条件均明确后，才开放该项测量。
- 测量前向用户说明完成该项测量所必需的准备和权限。具体操作提示按已验证的测量方法定义；技术参数不作为产品指标。

### 3.3 结果与客户端评估

- 测量结果应保留算法实际返回的原始读数、单位、测量时间、质量信息和固定算法版本。
- 客户端按与指标及算法版本关联的版本化规则计算参考范围和状态，不在页面组件中散布阈值判断。
- 规则必须声明适用人群、必要资料、单位、边界和缺失值处理。适用条件不满足时可显示合格的原始读数，但不显示未经支持的状态或参考范围。
- 低质量、无有效信号、算法失败、请求失败和没有测量记录必须区分；缺失结果不得补成零或默认健康值。
- 结果状态不构成诊断，也不自动生成个性化建议。

### 3.4 历史记录与趋势

- 记录以指标和单次任务区分，允许用户按指标查看已有测量结果。
- 历史原始读数不因评估规则升级而改写；每次查看时按当前规则重新评估，并显示规则版本和评估时间。
- 趋势只使用真实、有效且语义一致的历史读数；缺失数据不得补成零或示例值。
- 当前服务端接口没有普通用户删除任务或取消任务的能力；产品不得承诺尚无接口支持的操作。

### 3.5 隐私、权限与数据生命周期

健康资料、测量结果、采集文件和上传行为的说明、授权、保留期限及删除方式，必须在正式开放指标前纳入产品要求。当前细则尚未确认，不在本文件中假定默认保留期限或自动删除行为。

## 4. 指标需求矩阵

以下字段是每项指标开放前必须补齐的产品与算法契约，不代表当前接口已提供。旧项目结果字段仅作参考，不能直接当作新项目接口定义。

| 指标 | 产品目标 | 新项目结果字段与单位 | 质量信息与失败条件 | 适用范围与客户端规则 |
| --- | --- | --- | --- | --- |
| 血压 | 独立发起血压测量并查看结果。是否以收缩压、舒张压等多个数值呈现，需由新算法契约确认。 | 待新算法契约确认。旧项目的 `sbp`、`dbp` 不构成本项目契约。 | 待确认；必须区分结果有效性和质量拒绝。 | 待指标验证契约定义适用人群、必要资料、参考范围、状态及规则版本。 |
| 心率 | 独立发起心率测量并查看结果。 | 待新算法契约确认。 | 待确认；不得由采集文件存在推断质量合格。 | 待指标验证契约定义。 |
| 呼吸率 | 独立发起呼吸率测量并查看结果。 | 待新算法契约确认。 | 待确认；不得由采集文件存在推断质量合格。 | 待指标验证契约定义。 |
| 血氧饱和度 | 独立发起血氧饱和度测量并查看结果。 | 待新算法契约确认。 | 待确认；不得由采集文件存在推断质量合格。 | 待指标验证契约定义。 |

每项指标开放前至少满足：

1. 新项目算法和任务结果具有明确、稳定的字段、单位、精度及时间语义。
2. 成功结果的质量信息、质量失败原因和无结果语义已约定。
3. 适用人群与所需资料已由该指标的验证契约声明。
4. 客户端评估规则经过确认并有独立版本；边界值、单位换算、缺失资料和不适用人群行为均有定义。
5. 指标所依赖的实际测量路径已经验证；技术采集成功不等于指标结果有效。

## 5. 暂不纳入普通用户功能基线

以下能力目前属于技术验证或实现细节，尚未定义普通用户侧的产品价值和使用要求：

- 相机分辨率、帧率、曝光、传感器采样间隔等调试参数。
- 原始 PPG、传感器 CSV、视频文件路径和原生诊断状态。
- 无扰式被动后台录像。现有能力保存视频，不产生生理信号或健康指标。
- 传感器独立原始数据采集。现有规格明确不承担医学解释或跨源同步。
- 实时波形、临床诊断和个性化健康建议。

是否将被动采集或其他传感器能力转为普通用户功能，需另行说明使用场景、用户价值、授权和数据处理要求。

## 6. 待补充的产品要求

1. 为四项指标分别明确实际结果字段、单位、精度、时间语义及可能的多个读数组合。
2. 明确成功结果提供哪些质量信息，以及质量拒绝、无有效信号和算法失败的用户含义。
3. 根据各指标验证契约确认评估规则的适用范围、所需个人资料、阈值边界和规则更新流程。
4. 明确单项测量的使用前提、操作指引、预计时长和是否允许重新测量；不得从当前技术参数直接推导产品时长。
5. 明确健康资料和采集文件的用途、授权文案、服务端及本地保留期限、用户可执行的删除方式。
6. 明确尚未开放的目标指标是隐藏、标注不可用，还是在产品中展示规划状态。
7. 明确四项以外是否还有其他目标指标，以及每项新增指标的纳入条件。

## 7. 当前实现与规格边界

- 当前 `apps/native/App.tsx` 展示的是主动 PPG、被动采集和传感器验证入口，不是正式产品导航。
- `native-acquisition` 规格定义相机采样、CSV、低频提示和文件生命周期，不声明医学有效性。
- Android 传感器规格定义独立原始样本采集，不定义血压、心率、呼吸率或血氧结果。
- 被动采集规格定义无预览前摄录像，不生成像素序列或 PPG 文件，也不判断生理信号。
- 后端当前示例模型 `isExample=true` 的结果只有 `sample_count`、`duration_seconds` 和 `sampling_rate_hz`，不包含本文的四项健康指标或临床判断。
- 旧项目的血压流程文档记录的是旧仓库行为，不是本项目的模型、阈值、任务字段或验收标准。
- 前端主题令牌中对指标领域色的分类只表达视觉领域，不证明相应测量功能已经具备。
